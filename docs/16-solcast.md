## 1. Integration Method

**Cloud API — SolCast Rooftop Solar Forecasting API.**

SolCast (by DNV) provides solar irradiance and PV generation forecasts tailored to specific rooftop installations. The API produces 48-hour ahead forecasts (in 30-minute intervals) based on the registered rooftop site's location, tilt, azimuth, and installed capacity.

**Base URL:** `https://api.solcast.com.au`

**Key endpoint:**
- `GET /rooftop_sites/<resource_id>/forecasts?format=json` — 48-hour forecast in 30-minute periods
- `GET /rooftop_sites/<resource_id>/estimated_actuals?format=json` — estimated actuals (past 7 days) based on satellite data

**Forecast response structure:**
```json
{
  "forecasts": [
    {
      "pv_estimate": 1.234,         // kW — expected generation
      "pv_estimate10": 0.900,       // kW — 10th percentile (pessimistic)
      "pv_estimate90": 1.600,       // kW — 90th percentile (optimistic)
      "period_end": "2025-06-01T02:00:00.0000000Z",
      "period": "PT30M"
    },
    ...
  ]
}
```

The `pv_estimate` is the central (50th percentile) forecast. The 10th and 90th percentile values provide a confidence range.

## 3. Authentication Method

**API Key** — static Bearer token.

Each registered rooftop site gets a unique `resource_id` and an API key. Authentication via:
- `Authorization: Bearer <api_key>` header

The API key is long-lived and does not expire (unless regenerated). No OAuth2 or token refresh is required — simpler than Panasonic or Home Connect.

Credentials in `user.secrets`:
```lua
secrets.solcast = {
  api_key     = "your-api-key",
  resource_id = "your-rooftop-site-resource-id"
}
```

## 4. Polling vs. Event-Driven

**Polling — low frequency is critical.**

SolCast imposes **strict rate limits** on the free tier:
- **Free (Hobbyist) tier:** 10 API calls per day
- **Paid tiers:** Higher limits (50–1000+ calls per day depending on plan)

With 10 calls/day on the free tier, the maximum polling frequency is approximately **once every 2.4 hours**. In practice, polling every **6 hours** (4 calls/day) is recommended to stay well within limits and because forecast data does not change meaningfully more frequently than this.

**Implementation strategy:**
- Track last fetch time in module state (`_lastFetchTime`)
- Only fetch from SolCast API if at least 6 hours have elapsed since the last successful fetch
- Cache the forecast array in module state between polls
- On each resident poll cycle, derive the "current period" estimate from the cached forecast (no API call needed)

This means:
- API call: every 6 hours (4 times per day)
- Dashboard update: every resident poll (e.g. 60 seconds) using the cached forecast

## 5. Available Data / Controllable Parameters

### Read Only (SolCast is read-only)

**From `forecasts` endpoint (48-hour ahead, 30-min intervals):**

| Metric | Notes |
|---|---|
| Current period PV estimate | kW — expected generation right now (derived from forecast array) |
| Next N hours forecast | Sum or average over a time window |
| Today total estimated generation | Sum of all forecast periods for today |
| Tomorrow total estimated generation | Sum for tomorrow |
| Peak generation period | Time of max expected generation |
| Generation confidence range | `pv_estimate10` to `pv_estimate90` |

**Derived from forecast + Sigenergy actuals:**

| Metric | Notes |
|---|---|
| Forecast vs actual comparison | SolCast forecast vs Sigenergy measured PV — useful for calibration |
| Remaining today's generation | Sum of forecast periods from now to end of day |
| Self-consumption planning | Use forecast to optimise battery charge scheduling |

## 6. Estimated Implementation Difficulty

🟡 **Easy.**

- Simple API key authentication
- Single GET request with JSON response
- No OAuth2 or token management
- Main logic is:
  1. Fetch forecast array every 6 hours
  2. Find current 30-minute period in cached forecast
  3. Write `pv_estimate` for current period to UserParam

The polling frequency management (rate limit guard) is the only notable complexity — requires persistent module state for `_lastFetchTime`.

## 7. Known Limitations and Risks

- **Rate limit critical** — exceeding the free tier rate limit (10 calls/day) results in `429 Too Many Requests`. The script must rigorously enforce its own rate limiting using module state. A failed or restarted script that does not preserve `_lastFetchTime` could exhaust daily calls quickly.
- **Free tier constraint** — 10 calls/day limits forecast freshness to every ~2.4 hours. For most use cases (energy scheduling, dashboard display), 4–6 hour refresh is adequate.
- **Cloud dependency** — no local fallback. If SolCast is unavailable or the internet is down, cached forecast data remains stale. Implement a maximum data age check (`_forecastAge`) and display a staleness indicator on the dashboard.
- **Rooftop site configuration** — the SolCast site must be correctly configured with the rooftop's tilt, azimuth, and installed capacity for accurate forecasts. Inaccurate site configuration degrades forecast quality.
- **Multiple arrays** — if the rooftop has multiple arrays (different orientations), each may need a separate SolCast rooftop site resource ID, potentially doubling API calls.
- **UTC timestamps** — forecast `period_end` times are in UTC. The Lua script must convert to local AEST/AEDT time for display and comparison with Sigenergy actuals.
